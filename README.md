# dispatch-kubernetes

[Dispatch](https://github.com/muhammad-musa-ml/dispatch-api) is a multi-tenant webhook-delivery service I
wrote in Go on PostgreSQL. Its own repository runs it with Docker Compose on one machine, and its evidence
file lists what was never tested there: more than one host, schema changes under a running service, and
what happens when pods or nodes go away.

This repository runs the unchanged service on a four-node Kubernetes cluster on one laptop. Terraform
creates the cluster and installs two Helm charts, GitHub Actions lints and smoke-tests the result, and k6
measures what a rolling deploy (with and without the `preStop` sleep that protects it), a pod removal, a
container SIGKILL, a node drain and a bad release do to a client that keeps sending requests at a fixed rate,
and how the autoscaler reacts to a load step. It costs nothing and needs no cloud account.

The design, including the alternatives I rejected, is in
[docs/rfc/0001-dispatch-on-kubernetes.md](docs/rfc/0001-dispatch-on-kubernetes.md). It was written before the
charts. Section "Things I got wrong or found out" below says where the measurements changed it.

### How to read the table

- **Open loop.** k6 starts a new request on schedule whether or not earlier ones have finished (the
  `ramping-arrival-rate` executor), so a stall shows up as failed requests and long latencies instead of the
  client quietly slowing down. The rate is 40 requests per second for the fault scenarios; each request is
  `POST /v1/events` with a fresh idempotency key. A request is **failed** if it times out after 5 seconds,
  hits a transport error or returns anything other than 201.
- **Window.** The fault is injected 30 seconds into the load. "p95 in fault window" covers the 60 seconds
  that start at the fault (100 seconds for the bad-release scenario, which runs longer). "p95 with no fault,
  same window" is the same statistic over the same seconds of the baseline runs, because the machine is noisy
  enough that p95 alone says little (see Limits).
- **Error span** is the time between the first and the last failed request of a run. It is 0 when there were
  none.
- **Cluster back to desired state** is measured through the Kubernetes API, polled every half second from
  the moment the fault starts until every desired API pod is Ready and none is terminating. For the rolling
  deploy it is the duration of `helm upgrade --wait`; for the bad release it is the time from `helm rollback`
  until the pods are Ready again.
- **Fixed replicas.** The fault scenarios run with the autoscaler off and exactly 3 API replicas, so that
  the replica count is the same in every run. The autoscaler has its own scenario, with it on.
- **Ablation.** "Rolling deploy, preStop sleep removed" is the rolling deploy again with the chart's
  `preStop` sleep set to 0, to show what the sleep buys. It differs from the "rolling deploy" row in that
  one setting and nothing else.
- **Rate sweep.** One 60-second run of the no-fault baseline at each of four arrival rates. One run each,
  so it is calibration, not a result; it is there to show that the database was not the limit at the rate
  used for the fault scenarios.
- **Bad release.** `helm upgrade --wait` to an image that exits at once, with a rollout deadline of 45
  seconds that I chose (it is a parameter, not a result). "Upgrade to detection" is how long the command
  took to fail; it is a few seconds longer than the deadline, most likely because Helm runs the migration
  hook before it starts waiting (I did not time the hook separately). The rollback itself is the next figure.

### What the numbers do and do not say

- **Graceful disruptions cost the client no failed requests.** In the rolling deploy, the pod deleted with a
  zero grace period, the node drain and the bad release with its rollback, no run had a failed request. What
  makes that possible is in the chart: the `preStop` sleep and the termination budget (the pod stays in the
  Service until the endpoint removal has propagated, then drains), `maxUnavailable: 0` with a readiness probe
  (a new pod takes traffic before an old one leaves), and the PodDisruptionBudget (a drain evicts one API pod
  at a time). This is at 40 requests per second with 3 replicas; it does not say what happens at a rate
  where the database is the bottleneck.
- **The `preStop` sleep is what makes the rolling deploy free.** With the sleep set to 0 and nothing else
  changed, every one of the 5 rolling deploys failed requests, all of them connection failures (status 0),
  over an error span of several seconds, and the `helm upgrade` itself finished sooner (compare the two
  rolling rows). A pod that starts shutting down before the Service has stopped sending it connections
  refuses them; that is the failure the sleep exists to prevent, and the sleep costs a few seconds of deploy
  time. I did not trace individual connections, so the mechanism is the expected one and not a measured one;
  the outcome is measured.
- **An unplanned crash does cost something.** When the API container is killed with SIGKILL nothing
  announces it to the Service, so requests that reach the pod while its container is dead or restarting
  fail: every run had some, all but one of them connection failures (status 0), within a window of under a
  second. The kubelet restarts the container inside the same Pod and it is Ready again within a few seconds.
  Nothing in the chart prevents those requests; a client retry covers them. Dispatch's idempotency keys make
  such a retry safe, and in one run a request was answered with 200, which is what Dispatch returns for a
  repeated `Idempotency-Key`: the first attempt had been stored by the pod that was killed, and the same
  request arrived again. The HTTP client in k6 is Go's `net/http`, which resends a request that carries an
  `Idempotency-Key` when its connection died; I did not capture a connection trace, so that explanation is
  likely and not proven. The harness counts that 200 as failed, because it counts every status other than 201.
- Recovery after a container kill, a pod removal and a node drain takes seconds here. The images are already
  on every node and the cluster is containers on one host, so these times contain no image pull and no
  machine provisioning. A managed cluster would be slower; the ordering of the scenarios should carry over,
  the absolute times will not.
- **The autoscaler is slow next to the faults above.** In the load step the first scale-out decision comes
  roughly a minute after the step in the median run, and the first new pod is Ready soon after the decision
  (compare the first two rows of the autoscaler table), so the delay is before the decision and not in
  starting a pod. The three existing pods carried the step meanwhile, with no failed request in any run. I did
  not test a step large enough to overload them, and scale-in was not measured.
- p95 differences of a few milliseconds are inside the run-to-run noise of this machine.

## Architecture

```
laptop, Docker Desktop
├─ kind cluster "dispatch"  (Kubernetes v1.37.0)
│   ├─ control-plane          NodePort 30080  ──► host 18100 (manual curl)
│   ├─ worker 1  role=data    PostgreSQL 17, StatefulSet + 2 GiB volume
│   ├─ worker 2  role=app ┐
│   └─ worker 3  role=app ┴─  Dispatch API pods (3-8, autoscaled) + 2 demo-receiver pods
└─ k6 container on the "kind" Docker network ──► http://dispatch-control-plane:30080/v1/events
```

- `terraform/modules/cluster-kind`: the cluster and the preload of the three images.
- `terraform/modules/platform`: namespace, Secrets (random passwords generated by Terraform), metrics-server,
  the PostgreSQL release and the Dispatch release. It knows nothing about kind; its only input from the
  cluster module is the path of a kubeconfig, so a cloud environment would add its own cluster module and
  reuse it.
- `charts/dispatch-postgres`: PostgreSQL as a StatefulSet pinned to the data node.
- `charts/dispatch`: the API Deployment, Service, autoscaler, disruption budget, the migration Job and the
  demo receiver. Credentials are never in the chart; it reads Secrets by name.
- `docker/migrate`: the migration runner image. `docker/bad`: the image for the bad-release scenario.
- `bench/`: the load script, the fault-injection harness, the summariser and the probes.

Dispatch is not modified and not vendored. `DISPATCH_API_COMMIT` holds the commit that was measured
(`48d2678`), `scripts/fetch-dispatch.sh` checks out exactly that commit into `vendor/` (ignored by git) and
fails if the result is anything else, and `scripts/build-images.sh` builds the images from Dispatch's own
Dockerfile, inside Docker, so no Go toolchain is needed on the host.

## Decisions in the charts

| Object | Setting | Why |
|---|---|---|
| Deployment | `RollingUpdate`, `maxSurge: 1`, `maxUnavailable: 0` | a new pod must be Ready before an old one is removed |
| Termination | `preStop` sleep 5 s; `terminationGracePeriodSeconds` 30 = 5 sleep + 10 HTTP drain + 5 in-flight webhook attempt + 10 margin | the endpoint has to leave kube-proxy before the process stops accepting connections; 10 s and 5 s are Dispatch's own shutdown deadline and worker timeout, read from `cmd/api/main.go` and `internal/delivery/worker.go`. The image is distroless, so the sleep is the native `preStop.sleep` action |
| Probes | startup and liveness on `/healthz`; readiness on `/readyz` every 2 s, two failures | `/readyz` pings the database, so a pod that loses it stops taking traffic quickly. It does not check the schema, which is why the schema is applied before any new pod starts (below) |
| Resources | CPU request 250m, limit 750m; memory request 32Mi, limit 128Mi | the CPU request is what the autoscaler's percentage is relative to; sized from the `kubectl top` samples stored in the run files (see the CPU table in Results). Memory was not profiled; the limit is generous |
| Autoscaler | CPU 60 %, 3 to 8 replicas, scale-down window 60 s | Dispatch exports no metrics, so CPU is the only signal without changing the service. The scale-down window is shortened (Kubernetes' default is 300 s) so repeated runs finish |
| PodDisruptionBudget | `maxUnavailable: 1` | a drain evicts one API pod at a time |
| Migration | Job as a Helm `pre-install,pre-upgrade` hook; the runner applies each `*.sql` once, recorded in `schema_migrations`, in a transaction under an advisory lock | several replicas starting together must not race to migrate, and the schema must exist before a pod reports Ready. Migrations only move forward: `helm rollback` restores the previous image and does not undo a schema change |
| Spreading | `topologySpreadConstraints` over nodes, `ScheduleAnyway`; app pods on `role=app` nodes, the database on the `role=data` node | the drain scenario needs pods on more than one node, and a drained cluster must still schedule |
| Security | non-root, read-only root filesystem, all capabilities dropped, default seccomp, no service-account token mounted | none of these are needed for the experiments; they are the defaults a reviewer expects |
| Connections | `pool_max_conns=10` in `DATABASE_URL`; PostgreSQL `max_connections` 200 | without it pgx sizes the pool as `max(4, visible CPUs)`, which is 24 per replica on this machine (`results/pool-default.txt`); 8 replicas could then ask for 192 of 200 connections |

## Run it

Prerequisites: Docker, [kind](https://kind.sigs.k8s.io/) 0.33.0, Helm 4.3.1, Terraform 1.16.6, kubectl,
Git, a POSIX shell and Python 3.10 or later (the harness uses only the standard library). The versions are
the ones the results were produced with; `results/environment.json` records them.

```bash
bash scripts/build-images.sh                    # fetches Dispatch at the pinned commit and builds 3 images
terraform -chdir=terraform/envs/local init
terraform -chdir=terraform/envs/local apply -var image_tag=48d2678
export KUBECONFIG="$PWD/terraform/envs/local/kubeconfig"
kubectl -n dispatch get pods                    # 3 API pods, PostgreSQL, 2 receivers
```

To send one event by hand, take an API key from the Secret (a JSON object of key to tenant name; the first
key will do) and post to the NodePort mapped to port 18100:

```bash
key=$(kubectl -n dispatch get secret dispatch-app -o jsonpath='{.data.API_KEYS}' | base64 -d | grep -oE '"[^"]+"' | head -n 1 | tr -d '"')
curl -s localhost:18100/v1/events -H "Authorization: Bearer $key" -H "Idempotency-Key: demo-1" \
  -H 'Content-Type: application/json' -d '{"type":"demo.created","payload":{"n":1}}'
```

To repeat the measurements, set `MEASURE_LOCK` to the path of a lock file (the harness refuses to start a
timed batch without one; on a shared machine every timed batch takes it first, so batches do not overlap) and
run the scripts the reported batches were started with. A batch that finds the lock taken retries every 10
seconds; `MEASURE_LOCK_POLL` (seconds) shortens that, which matters when another process also takes the lock
and releases it again quickly. The exact command of every batch is also in the table "When and how each
batch was run" above.

```bash
export MEASURE_LOCK=/tmp/measure.lock
bash bench/run-all.sh            # capture-env, baseline, rolling, kill, drain, badrelease, hpa, summary
bash bench/run-extra.sh          # sigkill and rolling-nosleep, summary
bash bench/run-calibration.sh    # the rate sweep
python bench/summarize.py        # writes results/summary.md and results/summary.json
python bench/embed_results.py    # pastes the summary into this README
terraform -chdir=terraform/envs/local destroy -var image_tag=48d2678
```

The harness joins the `kind` Docker network, so k6 runs from the official `grafana/k6` image instead of a
host install.

CI (`.github/workflows/ci.yml`) runs `helm lint`, kubeconform on the rendered manifests, `terraform fmt` and
`validate`, shellcheck and a Python syntax check; builds the images from source; then creates a three-node
kind cluster on the runner, installs both charts, posts an event and waits until it is delivered, performs
a rolling upgrade, a release that cannot start (the upgrade must fail) and a `helm rollback`, and checks
that the rollback is in the release history and a final post succeeds (`scripts/smoke.sh`).

## Things I got wrong or found out

1. **`kubectl delete pod --grace-period=0 --force` is not a SIGKILL.** My first design called it "as if the
   process were killed". A probe on the running cluster (`results/kill/force-delete-probe.txt`) shows the
   container exiting with code 0 (Completed): the Pod object disappears at once, but the kubelet still stops
   the container normally. The scenario is therefore named "pod deleted, zero grace period", and the real
   process kill is a separate scenario that stops the container through containerd (`crictl stop --timeout 0`)
   and records the exit code. That scenario and the ablation without the `preStop` sleep were added after the
   first round of batches; both are rows of the table above.
2. **`terraform destroy` failed** when the Kubernetes and Helm providers were configured from the kind
   provider's endpoint and certificate attributes: during the refresh the attributes were empty. Passing the
   kubeconfig path instead fixed it, but that fix was tested on a checkout that already had a kubeconfig file
   (see item 7).
3. **`helm upgrade --reuse-values` keeps the previous chart's defaults**, so a changed default (the CPU
   request) did not apply. The harness and the smoke test use `--reset-then-reuse-values`.
4. **The load level needed a check, and the check that is on record came last.** A fault experiment says
   something about the platform only if the database is not the bottleneck. The table "Rate sweep used to
   choose the arrival rate" above is the no-fault baseline at four rates, one 60-second run each. At every
   rate no request failed and k6 dropped no iteration. PostgreSQL's CPU grew from a small share of its limit
   (2 CPUs, `charts/dispatch-postgres/values.yaml`) at the lowest rate to most of it at the highest, where
   p95 also rose; p95 at the lower rates stayed in one narrow band. The fault scenarios run at 40 requests
   per second, which uses a fraction of the database's limit, with the autoscaler off so that the replica
   count is constant; the autoscaler scenario steps from 10 to 60. I chose 40 from pilot runs that I did not
   keep, so the sweep is a re-measurement and not those runs. It was made after the fault batches, on
   2026-10-24 between 13:37 and 13:52 UTC, and one of its runs (the lowest rate) came before the ablation
   batch and three after it (start and finish times are in the table). The runs took turns through the lock,
   so no two of the timed runs on this cluster overlapped.
5. **Dispatch's default connection pool is sized from the CPU count** (see the Connections row above).
6. **`helm rollback --wait` returns before the failed pods are gone.** The CI smoke test checked right after
   the rollback that no pod still ran the bad image, and failed on two runs in a row: the pod of the bad
   release was still listed, with a deletion timestamp, for a couple of seconds. An earlier run had passed on
   the same code, so it was a race and not a change. I reproduced it on the local cluster, and the check now
   waits up to 60 seconds for that pod to be deleted; a pod that never goes away still fails it (tried both
   ways on the cluster).
7. **A first `terraform apply` from a fresh clone failed.** The applies I ran while building all passed
   because the first one had left a kubeconfig file in the working directory. With no file there, the
   Kubernetes provider refused its `config_path`: the file is written by the cluster, which Terraform had
   not created yet. I found it only by cloning the public repository into an empty folder and following this
   README. The cluster module's `kubeconfig_path` output is now unknown until the cluster exists, so the
   providers are configured after it. From a fresh clone I then ran the whole path again: image build,
   `apply`, the event example above (201, then delivered) and `destroy`.

## Limits

- **One laptop.** The four nodes are containers that share one kernel, one disk and 24 logical CPUs with
  everything else on the machine, including k6. Absolute latencies and recovery times describe this
  machine, not a cluster.
- **A shared machine.** Containers of unrelated projects were running during every batch (the count is in
  the Results section); `docker ps` at the start and the end of each batch is saved beside the results, with
  the names replaced by a count. Other timed work on the same laptop took turns with these batches through
  a lock file, but nothing serialises against processes that do not take it. This is why the baseline p95 over
  the same window varies from run to run, and why p95 differences of a few milliseconds mean nothing.
- **Five runs per scenario**, so the ranges are the honest statement of spread; there are no confidence
  intervals. Baseline and bad-release runs are 170 seconds long, the other fault scenarios 120; an
  autoscaler run is 30 seconds at the base rate followed by 240 at the raised rate.
- **Single PostgreSQL pod.** The experiments never disturb it.
- **Demo receiver.** It fails the first two attempts of every event by design, so the delivery load is three
  attempts per event on top of the requests being measured.
- **Not measured:** duplicate webhook deliveries after a kill (delivery is at least once, so a duplicate is
  possible after a lease expires; the harness does not count deliveries), a database failover, a real cloud
  cluster, autoscaler scale-in time, cold image pulls, memory use, CPU at idle, and behaviour with more than
  one tenant under load. The CPU figures are `kubectl top` samples taken while load was flowing, one per pod
  about every 15 seconds, and the k6 results count API responses only.
